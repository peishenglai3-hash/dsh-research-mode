# W03 · 二元对立与三准则裁决（CONFLICT MATRIX）

**方法：** 把 62 条 findings 的 `recommendation` 两两比对，只保留**互斥**（做了 A 就不能做 B，或 A 否定 B）的对子；再按三准则打分。
**判据（先写死再打分）：**

- **M 可维护**：不新增第二个真源；新不变量有自动命令可查；不新增第三方运行时依赖。
- **R 可修正**：回退 = 1 commit 或 1 开关；无数据迁移、不改既有 artifact 身份、不删已注册工具；语义变更须先有 ADR。
- **C 初心**：(a) 科研能力真增长 ＞ (b) 证据诚实 ＞ (d) 删繁就简 ＞ 仅 (c)；违反 (c) 强迫持久化则直接出局。

---

## O1 · 安全优先 vs 产品优先

| | |
|---|---|
| **正题** | `crit-sec` / `crit-algo`：导出会在篡改后的字节上重建自洽 manifest（SEC-01）；导入无上限、可压缩炸弹（SEC-02/ALG-04）；逐工具授权缺口仍在。先把这些关掉。 |
| **反题** | `crit-prod` / `HCI`：产品已 5 天没有新版本；首屏没有任何"第一条证据"的路径；继续做安全工程就是让工程纪律挤压科学活动。 |

**判定：** 两边**都过 M+R**——廉价的完整性修复（1 commit + 1 测试）与产品摩擦修复互不排斥，是**假冲突**，可排序。
**合题：** 先做**读路径完整性**（读时验字节、导出拒绝篡改）——已做；**逐工具授权框架**（C3）推迟，因为它不过 R（无 1-commit 回退，且要改协议）。产品摩擦的单点修复（面数一致、安装路径、CI）并行完成。

---

## O2 · 改字段语义 vs 只改文案

| | |
|---|---|
| **正题** | `crit-arch` / `ARCH-06`：`reproducibility.available` 恒为可用、`environment` 缺省填充，这两个名字**主动误导**；应加 `mode: recorded\|defaulted\|absent`。 |
| **反题** | `gap-ux` / `HCI-01`：字段语义一变就要迁移既有 sidecar、要 ADR、要让旧数据仍可读；先让界面和文档说真话，成本是零。 |

**判定：** 正题**不过 R**（改既有字段语义 = 需要 ADR + 可能迁移；旧 `.science` 里没有 `mode`，读取时得向上推断）。
**合题：** 本轮**不改字段**；把"记录值 vs 实测值"在**输出层**分开——`payloadVerified`/`payloadBytes` 已经加在 `provenance_get`（加字段、无迁移），`available` 在 UI 上标注为"有记录"。字段级 `mode` 留 ADR，写进 `W03-ITERATION-PLAN.md` 的推迟项。

## O3 · 合并重复 vs 不动发布拓扑

| | |
|---|---|
| **正题** | `gap-maint` / `ARCHC-04`：两个 client、两套 litdb 实现、两个 preset 差 13 行——同一件事多处实现，应抽共享模块。 |
| **反题** | `ARCHC-04` 自己给的边界：两个 client 属于**两个已发布的 npm 包**，抽共享代码要改发布拓扑；litdb 的 Node/Python 两套已经**行为分叉**（topK 20 vs 50），合并等于改语义。 |

**判定：** 正题**不过 M**（新增共享包 = 新真源 + 改发布拓扑，且未减少真源数）且**不过 R**（合并 litdb 改变对外行为）。
**合题：** 不合并。改为**把分叉钉住**：加一条差分测试固定"Node 顶 20 / Python 顶 50"这一既存事实，并写进文档；preset 的 13 行差异目前**保留**（两个用户选项是产品意图，不是重复）。

## O4 · 阅读闭环靠新工具 vs 靠配置

| | |
|---|---|
| **正题** | `gap-func` FUNC-01/02：没有工具承接"读全文/定位"，应新增一个只读的 `research_reading_note_record`。 |
| **反题** | 主控实测 P-07：MCP 转换**能成功**（115 s / 317 s），失败点是 **60 s 超时**；锚点→原文已经可用。缺的不是工具，是一个配置值。 |

**判定：** 正题**不过 M**（新增公开工具而不先验证现有路径；且新工具也解决不了 115–317 s 的延迟）且**不过 R**（新工具是 C2，需要单项审批且不可 1-commit 回退）。
**合题：** 改配置（`toolCallTimeoutMs: 600000`，已做）+ **把证据单位定在锚点级**，并用 `tools/w03/verify-reading-loop.mjs` 把"引用必须逐字来自解析输出"变成可跑命令。**页号**只存在于 CLI 结构化输出，作为外部预处理路径记录，不在本轮新增工具。

## O5 · 立刻发版 vs 等 CI

| | |
|---|---|
| **正题** | `crit-prod` PROD-04：一物四名、版本四处不一、无 CHANGELOG、侧车不记 recorder 版本——该发一个新版把口径统一。 |
| **反题** | `gap-maint` MAINT-05：基线**根本没有 CI**，"66 测试"是声明；在没有自动门之前发版是扩大不可验证面。 |

**判定：** 正题**不过 M**（发布不新增任何自动不变量，反而把未经门禁的产物推出去）。
**合题：** 先建 CI（已做，run `43005157360` success），再发布；发布仍限**改过的 bundle**，且 Release 里如实写"未含逐工具授权"。

## O6 · 修 Hub 面数 vs 显示细节

| | |
|---|---|
| **正题** | `HCI-02`：`available` 是界面上**唯一**的信任数字，两处不一致会直接读成"数据坏了"。 |
| **反题** | 通常的"显示细节不值得动 UI"直觉。 |

**判定：** 正题**过 M+R+C(b)**（纯前端、可回退、且直接服务"证据诚实"）。反题**不过 C**——它不是细节，它是用户判断可信度的**唯一依据**。
**合题：** 抽出纯函数 `faceSummary`，让 Hub 像 `provenance_get` 一样读时派生 review 面，并加三条测试（已做）。

## 汇总

| 对子 | 谁出局 | 合题落点 |
|---|---|---|
| O1 | 都不出局（假冲突） | 先完整性，再产品摩擦；C3 推迟 |
| O2 | 改字段语义（不过 R） | 输出层加 `payloadVerified`；UI 标注"有记录"；ADR 留档 |
| O3 | 合并重构（不过 M/R） | 差分测试钉住分叉 |
| O4 | 新增工具（不过 M/R） | 配置 + 锚点级证据 + 可跑验证器 |
| O5 | 立刻发版（不过 M） | CI 先行，之后只发改过的包 |
| O6 | "显示细节"论（不过 C） | 派生一致 + 测试 |

**没有一个胜者靠"更重要"取胜；每个出局项都是因为先违反了可维护或可修正。** 这正是三准则想要的效果：不让"初心"成为跳过工程约束的通行证。
